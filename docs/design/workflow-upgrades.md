# Workflow 版本升级设计

状态：0.3.3 CLI 提供独立升级入口；旧版 0.3.1/0.3.2 CLI 不提供升级命令。需求与工作请求按项目协议发布到 GitHub Issues；本文件保存维护所需的设计约束，不替代实施票据。

## 问题与边界

当前 `init` 拒绝已有目标文件或安装记录；`migrate` 只识别固定来源的旧 Loop Engineering Development 安装，拒绝已有 Graph Engineering 安装记录。二者都不能完成 0.3.1 → 0.3.2 的版本升级。新增独立 `upgrade`，保留原命令职责。

Installed Workflow（已安装工作流）属于项目。升级必须保留项目对 runner、事件、Prompt 和其他文件的修改；不通过删除安装目录再安装实现升级。CLI 负责本地文件和来源记录，不 commit、push、发布 npm 包或修改 GitHub Settings。

## 命令与版本

计划接口：

```text
graph-engineering upgrade [--to <version>] [--apply] [--project <path>]
```

默认只展示升级计划与 diff，不写入项目。显式 `--apply` 才应用；发现冲突时即使传入 `--apply` 也停止。

执行命令的 CLI 版本与项目安装版本彼此独立。目标版本默认是执行命令的 CLI 版本；`--to` 指定准确的已发布版本，不接受不确定的滚动目标。0.3.3 首次交付命令，下列命令可将已安装 0.3.1 的项目升级到 0.3.2：

```bash
npx --yes @tutar/graph-engineering@0.3.3 upgrade --to 0.3.2
npx --yes @tutar/graph-engineering@0.3.3 upgrade --to 0.3.2 --apply
npx --yes @tutar/graph-engineering@0.3.2 check
```

0.3.3 CLI 与项目目标版本彼此独立；升级与离线操作见 [CLI 说明](../../packages/cli/README.md#workflow-版本升级033-起)。已发布的 0.3.2 包不会被修改，也不要求 0.3.1 CLI 自身支持 `upgrade`。

首次支持 0.3.1 起的当前 schema 安装；同版本报告无需升级，降级、旧 schema 和无法核对来源的安装停止并解释原因。静态 `check` 不证明真实 Workflow 执行成功。

## 基线与来源记录

三方输入为旧版本原始模板、项目当前文件和目标版本原始模板。根据 `.github/graph-engineering/installation.json` 中的准确版本取得旧 npm 包，核对包身份、版本、来源提交及文件清单；目标包同样核对。允许提供本地包用于离线执行，不因网络不可用而猜测旧内容。通过 `--from-package <baseline.tgz>` 与 `--to-package <target.tgz>` 提供原始 npm 包；两个参数均提供时无需 npm 或网络。包内 metadata 不是真实性签名，离线资产须由操作者从可信发布来源取得并核对 SHA-512。

安装记录表达目标模板的安装来源，不表示项目文件与模板逐字一致。成功升级后使用目标包的版本、来源提交和文件清单更新记录；保留的项目修改仍可被 `check` 标记为 `UNVERIFIED`。下一次升级以该目标版本原始模板作为旧基线，不把合并后的项目文件当作原始模板。

## 三方合并规则

对旧模板和目标模板的文件路径并集逐项处理：

| 情形 | 结果 |
|---|---|
| 项目内容等于旧模板 | 应用目标内容；目标已删除则删除 |
| 上游内容没有变化 | 保留项目当前内容，包括项目删除 |
| 项目内容已等于目标内容 | 保留，无需重复改写 |
| 项目与上游均修改同一文本文件，修改可合并 | 保留双方修改 |
| 项目与上游修改无法合并 | 报告冲突，整套不应用 |
| 上游删除文件而项目修改了该文件 | 报告冲突，保留现场 |
| 上游新增路径在项目已存在且内容不同 | 报告冲突，不覆盖 |
| 路径不属于旧模板或目标模板 | 保留，不接管 |

存在冲突时展示冲突路径及 diff，不把冲突标记写入实际 Workflow 或 Action 文件。用户处理后重新生成计划，只有整套计划无冲突才应用。不能可靠执行文本合并的文件发生双方不同修改时按冲突处理。

## 应用与恢复

先完整读取三方输入并生成计划，再执行写入；写入前复核涉及的文件与安装记录未被再次修改，变化则停止并要求重新生成计划。保留恢复所需的原文件、存在状态和安装记录，全部文件应用成功后才更新安装记录。普通写入失败时恢复原内容及原安装记录，不报告成功升级。

该恢复承诺针对可捕获的写入错误，不声称多个文件的替换具备文件系统事务原子性，也不声称断电、进程强制终止时可自动恢复。

## 验证要求

实现票据须覆盖真实包资产的 0.3.1 → 0.3.2 升级，而不仅验证新项目 `init`。验证默认预览不写入、显式目标、离线基线、来源核对失败、同版本与降级规则、项目修改保留、新增与删除冲突、冲突时整套不写入、应用前现场变化，以及普通写入失败恢复。验证连续升级后仍以正确模板为旧基线。

成功场景必须包含 0.3.2 新增的 Development 本地 Action 与 Coding Skill 桥接文件，并更新目标安装记录；仅修改版本号或 Workflow 引用不能证明升级完成。实际 runner 认证与任务执行的验证仍属于运行验收。

决策依据：[ADR-0011](../adr/0011-preserve-project-changes-during-workflow-upgrades.md)。
