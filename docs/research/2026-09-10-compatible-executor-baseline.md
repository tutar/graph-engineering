# Compatible Executor 跨运行时能力基线调研

## 问题与范围

本调研为后续定义 Compatible Executor（兼容执行器）最小契约提供事实依据，对照：

- `openai/codex-action`：官方 GitHub Action 对 `codex exec` 的封装；
- DeepSeek Harness：公开的 Headless（无头）CLI 与 SDK 执行面；
- `anthropics/claude-code-action`：官方 Claude Code GitHub Action。

这里只记录截至 2026-09-10 可由一手文档与源码确认的能力和差异，不设计接口、字段名或适配器实现。研究快照分别固定到 `openai/codex-action` commit [`8636508`](https://github.com/openai/codex-action/tree/86365089eb2b84e0a8fb0717b304f8bdcb13b20e)、`deepseek-ai/deepseek-harness` commit [`d347e70`](https://github.com/deepseek-ai/deepseek-harness/tree/d347e703908d0406b7a7ef80e3a0e594d86b2215) 与 `anthropics/claude-code-action` commit [`19dda84`](https://github.com/anthropics/claude-code-action/tree/19dda84776b3518d98b8798e591daee763049ed3)。三者都仍在演进，特别是 DeepSeek Harness 明确标注 Developer Preview（开发者预览）并提示会发生兼容性破坏。[DeepSeek Harness README](https://github.com/deepseek-ai/deepseek-harness/blob/d347e703908d0406b7a7ef80e3a0e594d86b2215/README.md)

## 可确认的共同能力

三套执行面共同具备的最小事实只有：

1. 接受一个文本任务，并在指定或既定 Workspace 中非交互运行；
2. 在运行前由外部提供模型服务所需凭据；
3. 允许执行环境为模型配置某种工具能力及权限边界，但三者的权限词汇和强制层级不同；
4. 以进程/Action 成败暴露终态，并通过 stdout、Action output、执行日志或 Action 自有 GitHub effect 中的至少一种途径暴露成功结果；这些途径并不统一；
5. 运行期间可能修改 Workspace，因此调用方可以在运行后独立检查文件树、Git diff 与测试结果。

这组交集不包括 GitHub Issue/PR、branch、comment、Session id、Resume、完整 transcript、JSON Schema、推理流、MCP 配置形式、approval 或任何特定 sandbox 名称。

## Runtime-specific 扩展事实

- **Codex Action** 特有表面包括 Responses API proxy、`safety-strategy` 降权、Codex permission profiles、`codex-home`、Codex CLI 参数以及最终消息文件；它的 GitHub Action 契约当前没有 Session/Resume。
- **DeepSeek Harness** 特有表面包括可组合 profile/patch/plugin tree、持久 Session event log、stdio JSON-RPC SDK、完整事件/通知流，以及 Headless 的 stdout/stderr/exit-code 分离；公开 Headless 与 SDK 自动化入口当前都没有冷 Session resume 或输出 Schema。
- **Claude Code Action** 特有表面包括 GitHub 事件模式、内建 GitHub MCP/评论/文件操作、分支和签名提交、Claude settings/hooks/plugins、多云 provider 认证，以及明确暴露的 `session_id`/`--resume` 和 `structured_output`。

## 对后续决策的约束

以下是事实矩阵对后续 Compatible Executor 契约讨论施加的约束，不是接口提案：

1. **不能用首个执行器的 Action inputs 充当通用模型。** `codex-action` 的 `safety-strategy`/permission profile、Claude 的 `allowedTools`/GitHub modes、DSH 的 profile/preset/plugin composition 不是同一套权限抽象；强行一一映射会虚构等价保证。
2. **共同成功语义最多只能建立在可观察终态与可取得的成功结果上。** 三者都能暴露失败，但失败时不都保证有最终文本；DSH SDK 返回 typed Session events/notifications，Claude Action 另存完整 SDK message log，而 Codex Action 只直接输出最终消息。它们不是同一种 transcript 或结果模型；更细的 stop reason、token/cost、tool call 不能作为必选共同字段。
3. **Workspace 是共同边界，但“隔离”不是。** 三者都围绕 cwd/Workspace 执行；Codex permission profile、DSH file sandbox、Claude tool permissions 的网络、宿主进程、额外目录和配置加载保证不同。后续必须分别声明实际 Runtime 权限，不能只用一个 `workspace-write` 名称暗示等价安全性。
4. **Session/Resume 只能是可选能力。** Claude Action 原生暴露，Codex Action 未暴露，DSH Headless/SDK 也没有跨进程冷恢复入口。若 Workflow 依赖 resume，就会排除当前两个兼容执行面，或要求适配器承担超出上游公共契约的额外实现。
5. **结构化最终输出只能是能力协商或外层验证，不能假设普遍原生。** Codex 和 Claude 都有 JSON Schema 路径，DSH 当前只有结构化事件而没有 Schema-constrained final result；“事件是结构化的”不等于“最终业务结果按调用方 Schema 验证”。
6. **工具扩展的共同事实是“可配置”，不是“统一配置”。** 三者均可接 MCP，但配置位置、支持的 MCP features、命名、权限和启动生命周期不同；DSH 明确只桥接 Tools。公共 Workflow 若需要某个工具，应验证可用能力，而不是透传一份假定跨 Runtime 通用的配置文件。
7. **GitHub 副作用不属于执行器必然结果。** Claude Action 内建大量 GitHub effects，Codex Action 示例通常把最终文本交给后续可信 Job，DSH 本身不要求 GitHub。branch、commit、comment、PR 等应在后续单独决定由 Workflow 还是 Runtime extension 拥有，不能从“兼容执行”事实中推出。
8. **输出与副作用必须分开验收。** 最终 assistant 文本在三者中都只是模型输出；代码是否实际修改、测试是否通过、评论是否发布需要由 Workspace/GitHub 的可信观测确认。尤其 DSH SDK 明确不把 assistant response 因果绑定到某条 prompt，仅以 receipt-to-idle 区间聚合结果。
9. **版本与能力漂移必须可见。** 三个上游的字段和安全机制持续变化；Compatible Executor 后续若形成契约，至少需要让使用者知道所选 Runtime/适配器及其实际能力，而不能仅以“兼容”掩盖上游差异。

## 结论

事实支持保留多 Runtime 的 Compatible Executor 扩展边界，也支持把 `openai/codex-action` 作为第一个兼容执行器；但共同基线应停留在“文本任务 + Workspace + 外部凭据/权限配置 + 非交互终态 + 最终文本/Workspace 副作用可观测”这一层。

Session/Resume、Schema 输出、完整事件流、GitHub effects、MCP/Plugin 配置和各自的安全模型均不是三者交集。后续契约决策若把这些能力纳入核心，必须明确选择排除某些当前 Runtime；若保留兼容性，则需要把它们视为可选、可检测且由具体 Runtime 说明保证的扩展。
